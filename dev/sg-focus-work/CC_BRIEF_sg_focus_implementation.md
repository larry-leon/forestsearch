## Phase 2 — the new focus `maxeffCons`

Selection contract: **among candidates with
`Pcons >= pconsistency.threshold`, the largest effect; ties by `K`.**

Given V1, the filter is implicit and the key is just:

```r
if (sg_focus == "maxeffCons") {
  data.table::setorder(result_new, -hr, K)
  return(result_new)
}
```

* `sort_subgroups()` — as above.
* `sort_subgroups_preview()` — `setorder(-HR, K)`, same as `"hr"` / `"maxeff"`.
* **Do not** route it through the `maxeff` winner-only fast path
  (`subgroup_consistency_main.R` SECTION 8). Every candidate must be evaluated
  or the consistency gate is meaningless — that is the entire difference
  between `maxeff` and `maxeffCons` (see V4).
* No `hr*` canonical form. `maxeffCons` is its own canonical name, as `maxeff`
  is; the `hr*` canonicalisation exists only for the legacy Cox vocabulary.
* `selection_rule` stays restricted to `"neighborhood"` and inert — the
  existing `.validate_selection_rule()` already enforces this for anything
  outside `{hrMaxSG, hrMinSG}`. No change needed there; confirm it errors.

**Do NOT reuse `"eff"` for this rule.** Existing code passing
`sg_focus = "eff"` — including the 500-replicate simulation — would silently
switch from consistency-primary to effect-primary. No error, no warning, a
different subgroup. This is the single worst outcome available and must not
happen.

**Acceptance:**
* On a hand-built candidate table where the effect-argmax is NOT the
  Pcons-argmax, `maxeffCons` returns the effect-argmax and `hr` returns the
  Pcons-argmax.
* On a table where the effect-argmax fails the consistency floor,
  `maxeffCons` returns the highest-effect *qualifying* candidate while
  `maxeff` returns the failing one with `Pcons = NA`.
* `sg_focus = "maxeffCons", selection_rule = "pareto"` errors.

### MANDATORY: align the debias gate's re-selection

The Tier-2 gate does not resample a fixed subgroup -- it **replays the
selection step inside each MR draw** (`.fs_dg_select()`,
`fs_debias_gate.R:130-153`) so the winner's-curse correction accounts for
selection. The replayed rule must therefore be the rule the analysis used, or
the correction de-biases against a selection event that never occurred.

`.fs_dg_reselection_from_focus()` (`fs_debias_gate_methods.R:134-145`) maps
`sg_focus` to a gate rule via a `switch()` ending in a bare `hr_rule` fallback
(`"maxcons"` under the consistency engine).

**Add `maxeffCons = "maxeff"` to that switch.**

The gate's `"maxeff"` is `passers[which.max(beta[passers])]` -- argmax effect
**among passers**, i.e. already gated by the consistency-qualifying set. That
is exactly the `maxeffCons` rule. It is NOT the same as `sg_focus = "maxeff"`,
which is ungated. No new gate mode is required.

**Failure mode if skipped:** `maxeffCons` falls through to the bare `hr_rule`
default and the gate silently replays `maxcons` -- no error, no warning, and
every Tier-2 estimate de-biased against consistency-argmax selection while the
search used effect-argmax. Silent invalidity.

**Verify** what defines `passers` under the consistency engine. The mapping is
correct only if `passers` is the `Pcons >= pconsistency.threshold` set. If it
is something else, stop and report.

**Acceptance:** `.fs_dg_reselection_from_focus("maxeffCons", engine = "consistency")`
returns `"maxeff"`. Add a regression test asserting every accepted `sg_focus`
value maps to a rule explicitly named in the switch -- never to the fallback --
so a future focus cannot repeat this silently.

Commit: `feat: add sg_focus = "maxeffCons" (effect argmax among consistency-qualifying candidates)`

## Phase 4 — couple the thresholds (BEHAVIOUR CHANGE; land with Phase 3)

`forestsearch_main.R:886-887` currently reads:

```r
pconsistency.threshold = 0.90,
stop_threshold         = 0.95,
```

Adjacent lines, different values — a candidate in `[0.90, 0.95)` qualifies but
does not halt the scan, so a *lower*-effect candidate can be returned.

Change to a lazily-coupled formal:

```r
pconsistency.threshold = 0.90,
stop_threshold         = pconsistency.threshold,
```

R's lazy evaluation makes this track automatically if the floor moves. Do
**not** hardcode `0.90` — that re-breaks the moment a user sets
`pconsistency.threshold = 0.85`.

Check `.sync_args_call_all()` still captures `stop_threshold` correctly for
bootstrap reconstruction now that its default is a promise.

**Acceptance:** with `pconsistency.threshold = 0.85` and no explicit
`stop_threshold`, the resolved `stop_threshold` is 0.85.

Commit Phases 3+4 together:
`fix: disable early stopping for sg_focus = "hr" and couple stop_threshold to pconsistency.threshold`

## Phase 4b — smoke test (Quarto living document)

Build `quarto/smoke-tests/sg_focus_smoke_test.qmd`. **A Quarto living document
exercising the pipeline end-to-end, not testthat scaffolding** -- it should
render to a readable report a human can scan.

Primary dataset: **GBSG** (`survival::gbsg`, no external dependency,
reproducible). Where GBSG does not separate two rules, add a hand-built
candidate table and call the exported `sort_subgroups()` directly, so the
distinction is demonstrated rather than assumed.

Run with `debias_gate = FALSE` throughout to keep render time sane.

Sections:

**1. Legality matrix.** Every `sg_focus` value (`maxeff`, `maxeffCons`,
`maxcons`, `hr`, `eff`, `maxSG`, `minSG`, `hrMaxSG`, `effMaxSG`, `hrMinSG`,
`effMinSG`) crossed with every `selection_rule`
(`neighborhood`, `pareto`, `both`). Record accepted / errored plus the message.
Expected: non-`"neighborhood"` accepted **only** for the four `*MaxSG`/`*MinSG`
names.

**2. Selection results on GBSG.** One row per legal combination: selected
subgroup label, `n`, effect, `Pcons`, `n_candidates_evaluated`. This is the
headline table.

**3. Alias equivalence.** Assert `identical()` selections for
`eff` = `hr` = `maxcons`; `effMaxSG` = `hrMaxSG`; `effMinSG` = `hrMinSG`.

**4. `batch_size` invariance -- THE regression check.** For every `sg_focus`,
run `batch_size` in `{1, 8, 64}` and assert the selected subgroup is identical.
This is the defect that motivated the whole exercise; a failure here means the
fix did not take. Report as an explicit PASS/FAIL per focus.

**5. `stop_threshold` invariance.** For `hr`, `hrMaxSG`, `hrMinSG` (early
stopping disabled): explicit `stop_threshold` vs `NULL` gives identical
selections, and the explicit form warns. For `maxeffCons`: `NULL` vs
`pconsistency.threshold` gives identical selections.

**6. The foci are genuinely distinct.** Demonstrate on a hand-built candidate
table that `maxeff`, `maxeffCons` and `maxcons` return different rows -- one
where the effect-argmax fails the consistency floor, so `maxeff` returns it
with `Pcons = NA`, `maxeffCons` returns the highest-effect qualifier, and
`maxcons` returns the `Pcons`-argmax. If GBSG happens to make some coincide,
say so; do not manufacture agreement.

**7. Threshold coupling.** With `pconsistency.threshold = 0.85` and no explicit
`stop_threshold`, the resolved value is 0.85.

**8. Gate mapping (one assertion only).** `.fs_dg_reselection_from_focus()`
returns an explicitly named rule -- never the bare fallback -- for every
accepted `sg_focus`, and `"maxeffCons"` maps to `"maxeff"`. Gate behaviour
beyond this is out of scope.

**Acceptance:** the document renders cleanly and every assertion passes. Any
failure is reported, not worked around.

## Phase 5 — documentation

1. `NEWS.md`, under 0.2.0 — a **behaviour-changing** entry, not a tweak. 0.1.0
   is on CRAN; an existing analysis re-run under 0.2.0 can return a different
   subgroup. State: (a) `"hr"` no longer early-stops; (b) `stop_threshold`
   default now follows `pconsistency.threshold`; (c) new `maxeffCons`;
   (d) new `maxcons` alias.
2. `@param sg_focus` roxygen — document `maxeffCons` and `maxcons`, and state
   plainly that `"hr"` is **consistency-primary with effect as tiebreak**.
   That is what it does; users read the name as the opposite.
3. State in the `sg_focus` docs that `selection_rule` and
   `effect_neighborhood` apply **only** to `hrMaxSG` / `hrMinSG`
   (`effMaxSG` / `effMinSG`) and are inert elsewhere.
4. `pareto_frontier_explainer.qmd` — see the separate review; at minimum add
   the scope statement from (3) and the preview sort's `-on_frontier` key.
5. **`parallel_args$batch_size` is undocumented in `forestsearch()`.** Verified:
   `@param parallel_args` (`forestsearch_main.R:212-226`) lists only `plan`,
   `workers` and `show_message`; `batch_size` appears nowhere in that file's
   roxygen. Yet `forestsearch_main.R:1183-1193` validates
   `parallel_args$batch_size` and errors on an invalid value, and
   `subgroup.consistency()` documents it (`subgroup_consistency_main.R:233`).
   So the outer function most users call accepts, validates and acts on an
   undocumented argument -- one that, before Phase 3, changes the selected
   subgroup.

   Add a `\item{batch_size}` entry to `forestsearch()`'s `parallel_args`
   block. After Phases 3-4 it is purely a performance knob, and the
   documentation should say so explicitly: **it does not affect the selected
   subgroup.** Cross-reference the distinct `twostage_args$batch.size`.

6. **Disambiguate the two `batch` parameters.** `parallel_args$batch_size`
   (candidates per parallel batch) and `twostage_args$batch.size` (splits per
   Stage-2 batch) differ by one punctuation character and batch different
   units. The package author read one as the other during review, so the
   collision is a live hazard, not a hypothetical.

   Report (do not fix without sign-off):
   * Is `parallel_args` validated against a whitelist? If not, `batch.size`
     placed in `parallel_args` is silently ignored -- a no-op with no warning.
     `twostage_args` **is** whitelisted (`valid_ts_args`,
     `forestsearch_main.R:1227`), so the two lists are handled asymmetrically.
   * Recommend either a whitelist for `parallel_args` with a "did you mean"
     message, or a rename to remove the collision.

7. `devtools::document()`, then `devtools::check(args = c("--as-cran", "--no-build-vignettes"))`.
