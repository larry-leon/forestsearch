Stage P — parallel behaviour

P2: batch_size sweep (the decision point)

forestsearch() defaults stop_threshold = 0.95; with sg_focus = "hr" the batching logic forces batch_size = 1, so each future_lapply() call carries one candidate. The question is empirical: does the finer early stopping save more than the idle workers and per-candidate serialization cost?

Read the extra column: if evaluated stays low across all batch sizes, batch_size = 1 is doing its job and should be left alone. If evaluated is large and wall-clock falls sharply as batch_size rises, the default is costing real time on this hardware.

The selected field must be identical across every row. If it is not, batch size is changing the answer, and that is a correctness question that takes precedence over any timing.

What this evaluation did not measure

  • The adjusted Cox path (adjust_covariates, especially strata()). The fast engine does not apply there and no claim is made about it.
  • DINA and GRF. These findings concern the FS search and consistency stages only.
  • Any GLM outcome family beyond the one gated (run_glm = TRUE covers binary/OR). Continuous/MD and count/IRR are untested here.
  • Interaction with use_twostage = TRUE, which has its own screening logic.
